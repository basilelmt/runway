# Runway Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construire Runway, une web app locale de budget par enveloppes avec import CSV La Banque Postale, règles récurrentes, prévision de découvert et tri assisté par Claude, telle que décrite dans `docs/superpowers/specs/2026-10-02-runway-design.md`.

**Architecture:** Un moteur pur (`core/`) calcule soldes, prévision, rapprochement et tri à partir de données en mémoire.
Un serveur Hono (`server/`) persiste dans SQLite via Drizzle, expose une API JSON validée par des schémas zod partagés (`shared/`), parse les CSV et pilote `claude -p`.
Un client React (`client/`) consomme l'API via TanStack Query.

**Tech Stack:** Node 24, TypeScript 7, Hono 4, @hono/node-server, Drizzle ORM 0.45 + better-sqlite3 13, zod 4, Vite 8, React 19, react-router 8, TanStack Query 5, Recharts 3, lucide-react, date-fns 4, vitest 5, iconv-lite.

## Global Constraints

- Montants en centimes entiers, dates en chaînes `YYYY-MM-DD`.
- Soldes jamais stockés, toujours recalculés.
- Interface en français, euros, un seul utilisateur, aucune authentification.
- Claude uniquement via `claude -p --tools "" --output-format json --json-schema`, jamais via clé API.
- Jamais de fichiers dans `/tmp` : utiliser `tmp/` du projet.
- Pas de tiret cadratin dans les textes.
- CSS modules vanilla (pas de framework CSS), variables de design dans `client/src/styles/tokens.css`.
- Toute entrée d'API validée par zod ; toute erreur renvoie `{ error: string }` avec un code HTTP adapté.
- Tests : `npm test` doit passer à la fin de chaque tâche. Commit à la fin de chaque tâche.

### Task 4: Core : récurrence et prévision

**Files:** `core/recurrence.ts`, `core/forecast.ts`, tests.

**Produces:**
- `expandRule(rule, from: ISODate, to: ISODate): ISODate[]` (bornes incluses, respecte `start_date`, `end_date`, `interval`, `day_of_month`, `active`).
- `forecast(state, rules, today, horizonDays): ForecastResult` avec `ForecastResult = { days: { date, accounts: Record<id,cents>, envelopes: Record<id,cents> }[], alerts: { kind: 'account'|'envelope', id, name, firstNegativeDate, daysUntil, minBalance }[] }`.
  Point de départ : soldes confirmés d'aujourd'hui.
  Entrées futures : transactions `planned` dont la date ≥ aujourd'hui, et occurrences de règles strictement après `last_generated_date` (ou après aujourd'hui si déjà matérialisées), jusqu'à `today + horizonDays`.
  Les alertes sont triées par `firstNegativeDate`.

- [ ] Tests expandRule : mensuel le 31 sur février, hebdo intervalle 2, quotidien borné par end_date, règle inactive renvoie `[]`, start_date après `to` renvoie `[]`.
- [ ] Tests forecast : loyer -800 le 5 sur un compte à 500 → alerte le 5 avec `minBalance = -300` ; salaire le 28 remonte ; enveloppe Courses à 50 avec dépense récurrente hebdo de 60 → alerte ; aucune alerte si tout reste positif ; une `planned` déjà en base n'est pas comptée deux fois avec la règle.
